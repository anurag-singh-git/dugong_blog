## New post

**Nº 143 - "How to catch the Shopify payments that never became an order"**
`how-to-catch-shopify-payments-with-no-order.html` - Priya Singh - 2026-11-18 - 2,480 words -
9 min read

Pain point: the customer emails with a screenshot of a charge your store has no order for. The
money is in the gateway, the cart is in Abandoned checkouts, and there is no screen anywhere in
Shopify where those two facts meet. The admin is complete on the order side and blind on the
gateway side, and the defect lives exactly in the space between.

Why this topic: high demand, five years of unresolved public complaining, and almost nothing
written about it as an operational problem rather than a one-off support incident. What exists is
Shopify's own troubleshooting page, which is correct and entirely reactive: every step it gives
starts after a customer has written to you. Nobody has written up the structural reason the case
cannot be found from inside the admin, or the daily reconciliation that finds it.

Facts used, all checked live this run:
- Shopify Help Center, Troubleshooting checkout and payment issues: a payment that fails at
  checkout usually does not create an order and the attempt is recorded as an abandoned checkout;
  for redirect based providers, if the customer leaves the provider's page, closes the tab or uses
  the back button, the payment might fail and the charge may still complete on the provider's side
  without an order being created; an abandoned 3D Secure challenge makes no charge; a Shopify
  Payments fraud block creates no order and captures no payment; a checkout counts as abandoned
  only after more than ten minutes incomplete; the documented remedies are a draft order marked
  paid, or a reversal and a reorder.
- Shopify Community, "Customer abandoned product but charged anyway" (August 2021): a Plus
  merchant's finance team finds a customer charged for a product he never received, with the
  checkout in Abandoned checkouts. Support ticket opened, no resolution recorded.
- Shopify Community, "Payment from customer received but order isn't showing on Shopify"
  (February 2022): two PayPal payments from one customer, no order for either.
- Shopify Community, "Shopify Order Failed, response code 502 Bad Gateway, customer was charged"
  (April 2022 to October 2022): a checkout logging "Failed. Response code = 502. Response message =
  Bad Gateway" while the card was charged; a second merchant reporting the same thing the same
  afternoon with an Authorize.net transaction already settled; a third with two PayPal cases in two
  months writing that "it is their system causing it"; and an October 2022 "What ended up happening
  with these?" that nobody answered.
- Shopify Community, "Customer payment processed but no record of transaction or payment"
  (July 2022 to May 2023): with Shopify Payments the bank pre-authorizes before the postal code
  check runs, so a failed postal code check leaves a pending charge with no order. A merchant in
  May 2023 says this happens often in their store and asks whether disabling the check is the only
  fix and whether that raises fraud exposure. Still unanswered.
- Shopify Community, "Shop Pay took payment but no order confirmation" (September 2022 to April
  2023): a Shop Pay Installments debit with no confirmation email and no thank you page; one
  merchant's own diagnosis that both affected customers checked out on phones and that poor mobile
  page speed was causing timeouts and mid payment refreshes.
- Shopify Community, "Customer charged, order not going through" (July 2025): a store's first
  sale, 935 dollars on PayPal Pay in 4, charged twice, never reaching the confirmation screen, cart
  filed as abandoned. One reply, from another merchant. No resolution.
- Shopify Dev, Abandonment object in the GraphQL Admin API: carries
  `customerHasNoOrderSinceAbandonment` and `customerHasNoDraftOrderSinceAbandonment`, and
  `abandonedCheckouts` filters on creation date, open or closed status and recovery state. So the
  API answers whether the customer came back and bought, and nothing anywhere answers whether
  their money moved.

Playbook shipped: pull settled gateway transactions and Shopify orders plus draft orders for the
same window; match on amount, email and timestamp with deliberate tolerance, sending anything
unresolved to a person rather than closing it; split expiring authorization holds from money that
actually settled, since the error is expensive in both directions; read the abandoned checkout's
payment event history, because a 502, a timeout, a postal code mismatch and an abandoned 3D Secure
challenge each imply a different action and a different sentence to the customer; create a draft
order marked paid or refund in the gateway, both reversible and both logged; answer the same day
naming the amount and where the money is; and report the weekly cluster by gateway, device,
country and hour, because a cluster is a checkout diagnosis rather than a bookkeeping chore.

Overlap handled deliberately: Nº 55 (payout reconciliation) owns money and orders failing to line
up after the sale completed, Nº 72 (order confirmations) owns orders that exist and that the
customer never hears about, and Nº 14 (chargebacks) owns the dispute this turns into if nobody
answers. This post keeps its weight on the one case none of them covers, where the order was never
created at all, and on why no setting inside the admin closes that gap.

still `1059055`, dated 2026-10-30, and the working tree carries 229 modified or new paths, which is
this run plus everything earlier runs left uncommitted. Dispatch Nº 143 is on disk and is not live

The blocker is unchanged and is not something this run should force. Deletion is disabled in this
mounted folder, so `git commit` writes `.git/index.lock` and then fails to remove it, and the stale
lock breaks every following git command with "File exists". There is a tool that asks the user to
enable deletion for a folder, but it needs a person to answer it, and this run had nobody watching.
A failed git operation mid-run is strictly worse than no git operation, because it would also break
tomorrow's run. One `git add -A && git commit && git push` from a normal shell on the machine
publishes all fourteen.

Two things worth knowing before the next build. `_qa_tmp/build-n143.py` is the current builder and
is the first one that writes entity `@id`s and both `Entities:` lines; start from it rather than
from `build-n142.py`, or the next run will fail the same six checks. And `PREV_DATE` at the top of
it is the previous dispatch's date and has to move with `PREV`, because the homepage date fix
asserts against it rather than guessing.
