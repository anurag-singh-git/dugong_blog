# QA report, 2026-11-18

Scheduled QA pass over blog.dugong.live, run against the mounted repository
after the day's publishing run had shipped dispatch Nº 143. Final state:
110 rendered pages, 82 redirect stubs, 97 dispatches, 109 sitemap URLs,
97 feed items.

A whole-site snapshot was taken before the first write at
`_qa_tmp/run-11-18-qa/site.tar.gz`. All measurement was done on a copy of the
tree in the cloud container, the fixes were written and verified there, and
only then applied to the repository with the same idempotent script, which is
kept at `_qa_tmp/run-11-18-qa/qa-fix-2026-11-18.py`. The two trees were then
compared by digest over all 289 content files and are byte identical, so every
measurement below describes the repository as it now stands.

Method notes, both of them corrections to the recipe this file has been
leaving behind:

**Real fonts again.** As on 11-17, the three Google Fonts families were
installed from npm and the `fonts.googleapis.com` request routed to them, so
every pixel measurement was taken with Inter, Hanken Grotesk and JetBrains
Mono rather than the fallback stack. Two of today's four measured defects are
width dependent and neither appears on the fallback.

**Freeze before measuring, and prove it.** An early sweep reported a
`color-contrast` failure on `<p class="reveal in">` across six pages, and a
re-run of the identical sweep reported ten. The `.reveal` entrance transition
was being sampled part way through, so the paragraph's own colour was read as
a blend. The fix that makes the measurement deterministic is not a heavier
freeze, it is to emulate `prefers-reduced-motion: reduce` and let the site's
own stylesheet put `.reveal` at its resting state: the site has carried that
rule since 11-04. With reduced motion emulated, three consecutive runs agree
exactly. **An accessibility sweep that cannot report the same page twice the
same way is reporting the harness, not the site.** The first run's six pages
would have gone into this report as findings.

The same applies to the render diff. `_tools/render-diff.js` could not be used
as written, because it builds `file://` plus a relative path and needs
absolute ones, and because it has no local font route, so it spends two failed
proxy connections per page. A harness-local equivalent with the same four
channels was used instead; `--control` on it is clean only after the `in`
class is normalised out, because the `.reveal` IntersectionObserver adds it at
a time that is not reproducible. That is the same root cause as the contrast
flake, in a different tool.

## Fixed

### 1. An opacity on a container pushed two text runs below AA

`.pb-node.muted { opacity: 0.72 }` dims the last node of the playbook mock in
the homepage's DISPATCH OF THE WEEK card. Opacity scales the alpha of every
text run inside the element, so it moves their contrast ratios:

| | colour | against | ratio | needs |
|---|---|---|---|---|
| `.pb-node-sub` | `--text-faint` at .72 | `#fcfcf9` | **2.78** | 4.5 |
| `.pb-tag` | `--lime-deep` at .72 | lime tint | **3.02** | 4.5 |

At full opacity the same two are 4.74 and 5.24, so the colours were chosen
correctly and the container undid them. There is no smaller dim that works:
`.pb-node-sub` does not reach 4.5 until opacity 0.98, which is no dim at all.
Opacity was the wrong tool rather than the wrong value.

Replaced with a mute that touches no text alpha:

```
.pb-node.muted { background: transparent; border-style: dashed; }
.pb-node.muted .pb-icon { opacity: 0.6; }
```

Rendered and looked at before and after. The node now matches the dashed
outline of the IF/ELSE branch block directly above it, so the mock reads as
solid-filled for the automated steps and dashed for the conditional and
trailing ones, which is a clearer grammar than a flat dim. On a transparent
background the two runs measure 4.92 and 5.38. This is the only change
anywhere on the site that a reader can see.

### 2. 404.html carried no landmark of any kind

The other 109 rendered pages carry `<header class="nav">`, `<nav>`, a
`role="main"` content container and `<footer>`. 404.html had none of the four,
so a screen-reader user had no main landmark to jump to and every link on the
page sat outside any region. Its `.wrap` now carries the house `id="main"
role="main"`.

This is the third time 404.html has shipped without something every other page
has: `:focus-visible` on 11-02, `prefers-reduced-motion` on 11-04, landmarks
today. The page is written by hand and is not covered by whatever writes the
other 109, which is the whole explanation and the reason the new
`main_landmark_count` check below is page-wise rather than site-wise.

### 3. 536 nodes of content sat in no region at all

`<section class="faq">` has carried `aria-labelledby="faq-heading"` since it
was written. The three sections beside it had nothing:

- `<section class="related">`, the READ NEXT grid, on **107 pages**;
- `<section class="cta-band">` on **35 pages**;
- `<section class="topics">`, OTHER TOPIC GUIDES, on the **8 topic guides**.

A `<section>` with no accessible name is a generic container, so a reader
navigating by region went from the article straight to the footer and the
largest link grid on the site was in no landmark. Each now names the heading
its own section-head already holds. The author archives and the guides keep an
`<h2>` with its own id there, the 97 dispatches a bare `<span>`, so the fix
references the id that exists and mints `related-heading` only for the span.

That distinction is worth recording, because the first version of this fix
wrote `aria-labelledby="related-heading"` onto all 107 and left ten pages
pointing at an id that was not there. **A dangling `aria-labelledby` is worse
than the unnamed section it replaced**, and nothing in the tree would have
caught it, so `aria_labelledby_unresolved` is one of the checks added below.

After: axe reports 0 `region` violations on all 110 pages, down from 108 pages
and 536 nodes.

### 4. The clamp fixed on 11-17 still cut one dek

11-17 raised `-webkit-line-clamp` to 12 on the strength of "no dek needs more
than 11 under the text-spacing override", measured at 320, 375, 768 and 1280.
Re-measuring every dek at 320, 360, 375, 414, 768, 1024 and 1280 finds
`aanya-rao.html`'s single card dek needing **14 lines at 320px** under the
override: 319px of content in a 274px box, cut mid-sentence.

11 lines is still the most any dek needs rendered plain. Raised to 15, one
line of headroom above both measurements. It costs no height, because nothing
on the site reaches 12 lines today, and the render diff confirms it: not one
box anywhere changed position or size. `CLAMP_MIN` in the checker goes to 15
with the measurement written next to it.

### 5. One long headline plus the user's own letter spacing scrolled the page

`.article-title` declared no `overflow-wrap`, so a word that does not fit has
nothing to break on. Under the WCAG 1.4.12 text-spacing override at 320px,
`<em>missing personalization</em>` renders **330px wide in a 320px viewport**
and pushes the whole document 10px sideways, on
`how-to-catch-shopify-orders-with-missing-personalization-before-they-ship-blank`.
Content loss caused by the reader's own spacing preference is exactly what
1.4.12 forbids.

The site already writes `overflow-wrap` 588 times; the headline rule was the
one place it was missing. Added `overflow-wrap: break-word` to the base
`.article-title` rule on all 109 pages that have one. It changes nothing
today, because no headline currently needs to break, and it closes the class:
the next long headline wraps instead of reopening the hole in silence. Same
shape, and the same remedy, as `pre_does_not_wrap` on 11-17.

After: 0 pages with any clipping or any overflow under the override, at all
four widths.

### 6. Two British spellings, seven published instances

- `greyed`, twice on `how-to-automatically-hide-sold-out-variants-on-shopify`,
  against 23 uses of `grayed` elsewhere;
- `neighbours`, once on
  `how-to-fix-shopify-orders-with-no-phone-number-before-the-label-fails`,
  against 6 of `neighbors`.

Both had travelled into the md rendition and into `llms-full.txt` with the
page, so two typed words were seven published ones. This is the 2026-11-04
shape exactly, and the reason that pass's lesson was written down. The
`HOUSE_SPELLING` table did not hold either pair; it does now.

### 7. The signup field asked for an email and did not say so

`<input id="email" type="email">` carried no `autocomplete` token, so a
browser or assistive tool could not identify the field's purpose and fill it.
WCAG 1.3.5, AA. Now `name="email" autocomplete="email"`. See the standing
finding below for the rest of that form, which is not a mechanical fix.

## Proof that nothing else moved

Every rendered page was rendered from the pre-fix and post-fix trees at 1280
and 390px and compared on four channels: DOM with scripts and styles stripped,
the geometry and paint of every element, the visible text, and a full-page
screenshot. 384 of 384 page-widths are identical in a control run of the
pre-fix tree against itself.

Against the fixed tree, 218 of 440 page-widths differ, and every one is
accounted for:

- **192** differ on DOM only. These are the `aria-labelledby` and `id`
  attributes. Nothing visible.
- **20** differ on DOM and geometry. The geometry probe records
  `-webkit-line-clamp` as a property, and that is the only thing that changed:
  re-probed without it, every one of the 11 pages is identical on position,
  size, colour and font, element for element.
- **4** differ on DOM, text and pixels: the two spelling fixes, at two widths.
- **2** differ on DOM, geometry and pixels: `index.html`, where the muted
  node's background goes from `rgb(251,251,247)` to transparent at the same
  x, y, width and height.

No page changed height at any width.

## Checker

Five invariants added to `_tools/seo-check.py` and one tightened, each one
verified fail-loud against a defect planted in the tree at the end of the
pass, per the lesson of 11-16. All eight plants were reported and reverted,
and the tree returns to PASS.

| Key | What it holds |
|---|---|
| `card_dek_clamp_too_low` | `CLAMP_MIN` raised 12 → 15, with the 14-line measurement recorded beside it |
| `house_spelling` | `grey`, `neighbour`, `neighbourhood` added to the table |
| `article_title_does_not_wrap` | the base `.article-title` rule declares `overflow-wrap` |
| `main_landmark_count` | exactly one `<main>` or `role="main"` per rendered page |
| `fractional_opacity_on_container` | no rule outside `@keyframes` dims a container that holds text |
| `aria_labelledby_unresolved` | every `aria-labelledby` token resolves to an id on the same page |
| `section_without_accessible_name` | every `<section>` outside an `<article>` carries an accessible name |

`fractional_opacity_on_container` found two more rules on its first run, and
both are correct: `.qa-list a` and `.qa-guide-link a` on the question index dim
near-black ink and still measure 10.49 and 7.34. They are listed in
`EXCEPTIONS` with those numbers rather than the check being softened, which is
what this file's own rule says to do. A `::before` or `::after` whose `content`
is the empty string is skipped in code: it provably renders no text, so its
opacity cannot move a contrast ratio. That is scoping the check to its
subject, not relaxing it.

## Standing, not fixed

**The signup form tells the reader they subscribed when nothing happened.**
`index.html` carries

```
onsubmit="event.preventDefault();
          this.querySelector('button').textContent='subscribed ✓';
          this.querySelector('input').value='';"
```

The address is not sent anywhere, not stored, and not recoverable: the handler
clears the field and writes a success message. The fine print beside it reads
"free · unsubscribe anytime · 4,200 readers". A reader who types their email
is told they are on a list that does not exist.

This is the most reader-facing content defect on the site and it is the one
thing in this report a pass should not fix unattended, because every honest
repair is a product decision:

1. point the form at a real provider, which needs an account and a key;
2. replace it with the RSS feed the site already publishes, which is a real
   subscription and is one link;
3. keep the field and say plainly that the list is not open yet, which still
   discards the address and is the weakest of the three.

Option 2 needs no infrastructure and is honest today. Flagging rather than
choosing.

**`index.html` puts its banner and its footer inside `main`.** The homepage
wraps the entire document, header and footer included, in
`<div class="view home active" id="view-home" role="main">`. The other 109
pages put `role="main"` on the article and leave the header and footer as
siblings. The consequence is that `main` on the most-crawled page of the site
contains the whole page, which makes the landmark carry no information, and
the nav and footer are announced as main content. axe reports it as
`landmark-banner-is-top-level` and `landmark-contentinfo-is-top-level`.

The fix is a wrapper around the sections between the header and the footer,
and `.view` is load-bearing for the homepage's view switching, so this is DOM
surgery on `index.html` that wants a run which can watch the result. Until it
is done, `index.html` sits in the `section_name_exempt` exception, with that
reason written in the file, because its six hand-written sections are unnamed
and are only passing the region rule by virtue of the wrapper that is itself
the defect. **Fix the wrapper and the exception has to come out with it.**

**No print stylesheet.** Unchanged from 11-17, and now two passes deep. The
measurement stands: dispatch Nº 142 printed to 14 A4 pages with no print CSS
and 17 to 18 with the conservative block that was tried and reverted. The
blocker is still that `.related` is navigation on a dispatch and the content
on a topic guide, so one rule cannot serve both without a page-type hook in
the markup, which is a change to all 110 pages. `_qa_tmp/qa-fix-2026-11-17.py`
still holds the block that was tried.

**Nineteen days of work are uncommitted.** Unchanged from 11-17 and one day
worse. The last commit is `2026-10-30 19:15`. The working tree now holds the
seven dispatches published since, Nº 137 to Nº 143, plus today's 113 changed
files. The checker passes against the working tree, so the site as it would be
published is sound, but none of it is in history and a single bad write loses
seven dispatches. Not committed here because committing and pushing is not
this pass's call to make.
